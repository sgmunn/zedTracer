## Decisions taken

- Grid on `ui::Table`; do not use `tabular_data_preview` (UI-1). Header: own right-edge resize handle, no change to `ui` (UI-2). Sort, filter, search run in a background task with a generation number (UI-3).
- Row Details is a right-dock panel following one shared `ActiveSelection` (UI-4). It opens whenever a result is shown (RDT-13): `display` in `run_query.rs` opens it with the Results panel, and `ResultsViewer::added_to_workspace` opens it for a tab, once per tab (`offered_row_details`) because moving a tab to another pane adds it to the workspace again. The tab can only ask the workspace to open the panel after the update that is adding it has finished, hence `Window::defer`. The inspector is one read-only editor with a header line per field; keep borrowing existing editor highlight keys (UI-5). Filter popover is a `PopoverMenu` with its own view and its own outside-click handling (UI-6). Text copy is P0; rich HTML copy is P1 and needs clipboard platform work (UI-7).
- Execution is native Rust over the Kusto v2 REST API, not a .NET process and not the language server; tokens come from `az account get-access-token` (decided with the user). The language server loads its own schema over REST, also signing in with `az`.
- The editor and the language server share no channel: the editor appends run records to `kusto/history/runs.jsonl` and the server reads it (code lenses). A lens that must act in the editor names a Zed action in the `zed.dispatchAction` lens command.
- Every run is saved to the history folder first and the Results panel opens that saved file, so a panel result keeps its layout and can be shown again from history (the user's decision).
- A file is a set of queries separated by blank lines; the run command, the lenses and every language feature use the same rule (`QueryBlocks`, `query_range_at`). A blank line does not end a query while a `(` or `{` the query opened is open, or a multi-line string (triple backticks or `~~~`) is (the user's request: the lens appeared in the middle of a function body with a gap in it until the gap was filled with `//`). The scan skips comments and strings (a quote ends with its line, `@'…'` has no escapes) and counts brackets of one kind in one counter. Brackets still open at the end of the text are no gap: the query ends at its first blank line, so a bracket left open while typing cannot join every query below it. The cost is one extra scan to the end of the text per such query. `[` and `]` are not counted. Rust (`query_text.rs`) and the server (`QueryBlocks.cs`) implement it twice and are tested against `fork-docs/samples/query-blocks.json` (Rust through the first and last line of each query, the server through the line each query's lens is above). The test helper `query_line_ranges` in `test_server.py` still splits at every blank line and is only used on texts without a gap.
- Where a query runs comes from comments in the file, `// :setDefaultCluster("…")` and `// :setDefaultDb("…")` (the user's decision, after another Kusto extension): the form is `// :setDefaultCluster("…")` because Zed continues a comment with `// ` when Enter is pressed, and `//:` is accepted too; a directive applies to every query below it until a later one overrides it, setting the cluster clears the database, and the settings `kusto.cluster` and `kusto.database` are the defaults before any directive. A block of only comments is not a query. Rust (`crates/kusto_client/src/directives.rs`) and the server (`ConnectionDirectives.cs`) implement it twice and are tested against one file, `fork-docs/samples/connection-directives.json` (and `parameter-directives.json` for the parameter directives, see Query parameters). A lens shows each query's connection, and the run log's last run is keyed by cluster, database and query text.
- **Functions as files (built, asked for by the user):** the functions of a database are kept as `.create-or-alter function` files in the project, for git and for go to definition (the user's decisions: a snapshot "in the repo" that F12 creates and opens; a setting that is a project-relative folder or a full path, the default `kusto-schema` in the project, a full path used with no project, and a message when there is neither; entities are only for seeing their definition, tables may get an explorer later). It is the server's, because it already has the cluster sign-in, the schema and the project folders (`FunctionSnapshots.cs`: folder, text and files; `Definitions.cs`: F12, the lens command; `SchemaManager.ReadFunctionsAsync`). Probed first against `help` / `Samples`: `.show functions` has `Name, Parameters, Body, Folder, DocString`; `Folder` is null, empty or written with backslashes (`Packages\ML`), `DocString` is null or empty, and bodies are `{ … }` with CRLF and trailing blanks, which the file normalises. `KustoFacts.GetStringLiteral` quotes with single quotes. The token of a name is wrapped in a `TokenName` whose parent is the `NameReference` (the first version looked at the token's parent and never matched), and its `ReferencedSymbol` is the very `FunctionSymbol` in the database's members, also through `cluster().database()`, which is how the owning cluster and database are found; a name the file defines with `// :functions` is skipped, since it hides the stored one. Each file starts with `// :setDefaultCluster` and `// :setDefaultDb` so that running it (F5) deploys to the database it came from. F12 never replaces a file; only when the function has no file does it write the missing files of the database (once at a time per place, the answer sent when ready so that other requests do not wait for the network). The **Snapshot functions** lens (`kusto.snapshotFunctions`, with the document's uri, which says which project) rewrites every file and reports new, changed, unchanged and files with no function; it does not delete them. The option is `snapshotDirectory` in `lsp.kusto-lsp.initialization_options`, not a `kusto.*` setting: those reach the server through the one global `defaults.json`, and a relative folder needs the project of the document. Tests: `SnapshotTest` (12, against the fake cluster, with the never-replace rule checked by turning it off). F12 was tried in a real Zed window by the user and works. Known gap: the server cannot tell a project from a single file opened alone, because Zed gives it the file's folder as the project root, so such a file gets `kusto-schema` beside it unless the option is a full path. Not built: go to definition for tables and entity groups (the same files would do), for functions defined in the file (a jump to the `let`), and the explorer.
- **Outline and Cmd+T (built, asked for by the user):** `textDocument/documentSymbol` and `workspace/symbol` in `Symbols.cs`, switched on for Kusto with `"document_symbols": "on"` in `assets/settings/default.json` (so it is in the Zed binary, not the extension). Zed uses a symbol's name, kind and `selectionRange` (the `detail` is ignored) and colours the name from the buffer text it finds in that range, so a query's name is the text of its label and the range is that text. A query is called by the first comment above its code that says something (not a directive, a line of dashes or an empty comment), else its first line of code cut at 100 characters (the first version took a comment anywhere in the block, so a line commented out in the middle of a query named it and the outline jumped there; found by the user in the outline picker); a `// :functions` block gives one entry per definition (`InlineFunctions.Locate` now says where each statement and name are); a command that defines a function is that function (`NameDeclaration` followed by `FunctionDeclaration` under the command, probed: the name's `TextStart` leaves out the leading newline). Notes and directives alone are not entries. Cmd+T lists the functions with a file under each project's snapshot folder (or the one full path), read from disk with no network, and, added when the user found Cmd+T only repeated Cmd+P (every function file is named after its function), the queries and `// :functions` definitions of every `.kql` file in the workspace folders (`ProjectSymbols.cs`: the symbols of `Outline.Of` kept per path by modification time and size, the file list kept 5 s because the picker asks again with every letter, open files read from the editor, folders that start with a dot, `bin`, `obj`, `node_modules`, `target` and the snapshot folders skipped, at most 5,000 files and 20,000 folders; 0.12 s cold and nothing cached on this repository's 966 folders), best match first (name, prefix, contains, letters in order), at most 200; a function's range is the name line of its file, found by reading only the files returned, and a file symbol's is its name. Zed filters the returned symbols by their name only (`symbol.label.filter_text()` in `project_symbols`), so only names can be searched, not the text of a query. Zed asks only the servers of visible projects, and a symbol outside the project is allowed. Because a symbol is a place in a file, a function with no file is not listed. Tests: `OutlineTest` (9), `ProjectSymbolTest` (6; the cache and the skipping of the snapshot folder checked by turning each off) and five in `SnapshotTest`, with the label and the ranking checked by turning each off; also run against the help cluster (47 files, `Covid` finds two). Tried in a real Zed window by the user and working: the outline, Cmd+T over the snapshot functions and Cmd+T over the queries of the project's files (which showed only the functions until the installed server was replaced by one built after the change). Not built: an entry for each statement of a query, tables and entity groups as symbols, and nesting a query's `let` statements under it.
- The grid fills itself with the theme's `editor.background` (`ResultGrid::render`) instead of showing the Results panel's `panel.background` through it (the user's decision: the panel colour looked grey). There is no setting for it; the theme override `editor.background` changes it, along with the editor. Not looked at in a real window.
- Judge speed in a release build; see "Known issue" below.
- Trace columns: `kusto_results.trace_columns` lists, per role (marker, message, severity, ...), the column names to try in order before the built-in names (TRC-7), so one setting serves tables that name a role differently. ## Running queries (first slice of phase E)

Decided with the user: execution is native Rust over the Kusto v2 REST API (not a .NET process, not the LSP), and the first version gets tokens from the Azure CLI.

- `crates/kusto_client` (UI-free, tested): `KustoClient::execute` posts to `/v2/rest/query` and returns a `kusto_results::ResultSet` (primary tables only; repeated `PrimaryResult` names become `PrimaryResult_2`, and so on, because saved table views are found by name). `KustoClient::cancel` sends `.cancel query "<client request id>"` to `/v1/rest/mgmt`. The token audience is read from `/v1/rest/auth/metadata` (`KustoServiceResourceId`, `https://kusto.kusto.windows.net` for every cluster tried, Fabric eventhouses included) and falls back to the cluster address. `TokenProvider` is the seam; `AzureCliTokenProvider` runs `az account get-access-token` with the project's shell environment, because a desktop app does not inherit the `PATH` where `az` lives. Error bodies are reduced to the innermost service message. `query_range_at` finds the query around the cursor: the run of non-blank lines, with a cursor on a blank line belonging to the query above.
- Results panel (`results_panel.rs`, `ResultsPanel`): a bottom-dock panel, registered in `initialize_panels` in `zed.rs`, that shows the latest run: an empty state (`No results`), the result in the same `ResultsViewer` a tab uses (with a one-line summary: cluster / database, rows, duration, start time) or the error of a failed run. Its badge is the row count, or `!` after an error. `kusto::ToggleResults` shows and hides it (no key binding yet). The setting `kusto.results_location` is `panel` (default) or `editor` (a tab per run, as before); without the panel registered, results fall back to tabs. A run opens the panel without taking focus, so the query stays in front and F5 works again; it opens Row Details too (RDT-13), but not for the error of a failed run. The panel does not read the response directly: every run is saved to `<data dir>/kusto/history/*.ktt` first and the panel opens that file the way a tab does (`ResultsFile::try_open`), so a panel result keeps its column layout, follows outside edits, and any history file can be shown again with `ResultsPanel::show_result`. A result with several tables shows the first in the Data tab and each further table in a **Data 2**, **Data 3**… tab (PNL-4): `ResultsViewer` keeps a `ResultGrid` for each table after the first (`extra_grids`, `ViewMode::ExtraData`), built with `GridOptions::secondary` so such a grid offers no Focus and dims no structural rows. Structured, Sequence, Timeline, the findings and Focus still read the first table only. Not built: a Query tab (PNL-6), Save As, a history list to pick an older result, moving the panel to another dock.
- `crates/kusto_results_ui/src/run_query.rs`: the `kusto::RunQuery` action (F5 and Shift+Enter in `.kql` editors, in the three default keymaps) runs the selection, or the query at the cursor, on `kusto.cluster` and `kusto.database` from settings (a project's `.zed/settings.json` works). A "Running query on <cluster>…" toast offers Cancel. A successful run is written to `<data dir>/kusto/history/<UTC time>-<uuid>.ktt` and opened in the existing results viewer, so each result lives in its own tab (RUN-5) and the file is a normal `.ktt` (PER-2). Failures are shown with `Workspace::show_error`. A cancelled run shows nothing (RUN-3).
- Live check, not run in CI: `cargo test -p kusto_client --test live -- --ignored --nocapture` runs real queries against `help.kusto.windows.net` with your `az login`.

Not built yet: query parameters (`declare query_parameters`, profiles), choosing a cluster or database from a list (settings only for now), a per-document connection, history browsing, rerun from a saved result (RUN-8), the per-query inline actions (RUN-9), the minimum-500 ms indicator, and a sign-in that does not need the Azure CLI. A long-running response is parsed whole; progressive frames are not requested.

## History

`kusto::ShowHistory` opens a picker (`history.rs`) of the runs in `runs.jsonl`, newest first (`kusto_client::history_entries` folds the records of a run into one entry; cancelled and unfinished runs are not listed). A row is the comments the query starts with (not directives) and then its first line of code, then `time · rows, duration · cluster / database` (or `failed: <first line>`, or `result moved or deleted`); typing filters on the query, cluster, database and error. Enter shows the result through `display` (the panel, or a tab by the `results_location` setting), the secondary Enter opens a tab, and a hover trash button deletes the file. The lens `Results` and the picker say so when a file is gone.

Rerun (RUN-8): a hover play button dispatches `kusto::RerunQuery { query, cluster, database, parameters }`, which `run_query.rs` handles by `launch_run` (the code `start_run` shares: `start_run` reads the editor, a rerun supplies a `RunSpec` with `ParameterSource::Values`). The values of the original run are kept in the `parameters` field of the run log's `started`, `finished` and `failed` records (left out when there are none; the server ignores the field) and carried into `HistoryEntry`, so a rerun repeats the run even after the active profile changed. The query text in a rerun is the stored text, comments and all, so its lens matches the original.

Keeping a result: `kusto::SaveResult { path?, suggested_name? }` (`save_result.rs`; `Save a copy…` in the viewer's tab bar, a download button on a history row, or the palette) asks where with `Workspace::prompt_for_new_path` (which opens in the folder of the most recently active file, so normally the work folder), suggests a name from `suggested_file_name` (the query's `history::title` slugged to 48 characters at a word, plus the local start time), and copies the file with `fs.copy_file`, overwriting what the prompt confirmed; a toast offers to open the copy. Pruning only reads the history folder, so a `.ktt` outside it is never deleted. A result file now carries what is needed to understand and repeat it: `KustoClient::execute` writes `parameters` (the string values; the field already existed in the `.ktt` format) next to `query`, `cluster` and `database`. `ResultsViewer` (`results_viewer.rs`) shows a tab bar for every usable result, with `Data`, `Structured` when the table has activity columns, `Query` when the file names a query (`query_view.rs`: a read-only editor, under a line saying where and when it ran and the parameter values), and at the right `Run again`, which dispatches `kusto::RerunQuery` built from the file (`rerun_action`; it needs query, cluster and database). 

Pruning (`kusto_client::files_to_prune`, run by `history::prune`): after each successful run and at startup, the oldest results past `kusto.history_max_results` (50) or `kusto.history_max_megabytes` (1024) are deleted, 0 meaning no limit; the newest result is always kept; only names of the form `<YYYYMMDD>-<HHMMSS>-<uuid>.ktt` are considered, so hand-saved files and `runs.jsonl` are safe; results open in the workspace that ran (tabs and the panel) are kept but count against the limits.

Found on the way: a result opened from the history lives in a single-file invisible worktree, which a project holds only weakly, and `ResultsFile` held it weakly too, so reloading and writing a column layout back could silently stop. `ResultsFile` now holds the worktree.

## Colours (semantic tokens)

The old tree-sitter grammar (`Willem-J-an/tree-sitter-kusto`) covered only part of KQL: a `let` statement or a tabular pipeline with twelve operators. Parsed with the real grammar (compiled in a scratch dir), `declare query_parameters`, `print`, `.show` commands, `take`/`top`/`count`/`parse`/`render`, member access on a call and a second query after a blank line (no `;`) were all errors, so colours were missing wherever recovery failed. The server now sends colours instead: `SemanticTokens.Build` runs `KustoCodeService.GetClassifications` for each query block with the globals of that block's connection and maps `ClassificationKind` to a legend of 12 standard token types (`comment keyword string number type class namespace function property variable parameter operator`); punctuation, plain text and unplaced identifiers get no token. Tokens are split at line ends (multi-line strings), exclude `\r`, and count UTF-16 units. Capability `semanticTokensProvider { legend, full: true }` (no delta or range); the server sends `workspace/semanticTokens/refresh` when a schema load starts or ends, and when the defaults change, once the client has sent `initialized`. Zed side: `assets/settings/default.json` has `"Kusto": { "semantic_tokens": "full" }` (tree-sitter off for the language; "combined" would layer on a grammar), and Zed's default `semantic_token_rules` map the types to the theme. The tree-sitter grammar, its `highlights.scm` and `test-highlighting.sh` are removed (the language has no `grammar` in its `config.toml`, no `[grammars]` in `extension.toml`; Zed's own manifest and language-config parsers were run against the result). Consequences: no colours before the server starts or without it installed, and the Query tab of a result is plain text (it set the Kusto language on its buffer, which only ever coloured through the grammar). Not built: delta and range requests (a large file is tokenised whole on each change), modifiers (`defaultLibrary`, `declaration`), and colours in the Query tab of a result (a read-only buffer the server never sees).

## Control commands

A block whose first non-comment line starts with `.` is a control command (`kusto_client::is_control_command`). `KustoClient::execute` posts it to `/v1/rest/mgmt` instead of `/v2/rest/query` and reads the v1 response (`parse_management_response`); nothing else in the editor distinguishes commands from queries (history, rerun, save, lenses, the Query tab all treat them alike, as decided). Two things found against the real service, both with tests: the service rejects a comment before the dot (`SYN0100: Admin commands must have a dot (.) character as their first non-whitespace character`), so `command_text` sends the command from its first line of code while the stored text keeps the label comments; and a v1 response holds the result followed by properties and status tables and a table of contents (columns `Ordinal`, `Kind`, `Name`), which the parser uses to keep only the `QueryResult` tables, named `PrimaryResult`, `PrimaryResult_2`, and so on. Column types come from `ColumnType`, else from the .NET `DataType`. The ignored live test `runs_control_commands` covers `.show tables`, `.show functions` with a label, and a missing function. Not built: cancelling a running command (`.cancel query` is for queries and is only tried), and schema-aware checks of commands (the server only checks their syntax).

## Schema-aware diagnostics

`Program.DiagnosticsOf` runs per query block: with the connection from the block's directives and the defaults, `KustoCode.ParseAndAnalyze(text, schema.GlobalsFor(connection))` and `GetDiagnostics()` (syntax and semantic) when `SchemaIsLoaded` (`SchemaManager.IsLoaded` for the query's own cluster and database, and for every `GetClusterReferences`/`GetDatabaseReferences` entry, using the per-database status that the `↻ Schema` lens also reads); otherwise `KustoCode.Parse(text).GetSyntaxDiagnostics()` as before. Control commands (`QueryBlocks.IsControlCommand`, the same rule as `kusto_client::is_control_command`) and the `schemaDiagnostics: false` initialization option stay syntax-only. A loaded schema is what makes a missing name an error, because `DatabaseSymbol(isOpen: false)` only exists for a database that was loaded; an unloaded one stays open and accepts any name. `SchemaManager.Changed` (a load starting or ending, and so a refresh) makes the server publish diagnostics again for every open file, once the client has sent `initialized`.

Knock-on errors (`KnockOnErrors.cs`): when the leftmost expression of a statement's pipeline (`ASEdog().ASTrace` in `ASEdog().ASTrace | where …`, also the right-hand side of a `let`) has an unresolved-source error (`KS204`, `KS211`, `KS143`, `KS208`–`KS210`, `KS247`, `KS248`), the `KS142` (unknown column), `KS107` (type expected) and related scalar/tabular-expected errors after it in the same statement are dropped, because the analysis cannot know an unknown source's columns. Other statements, and errors inside a query with a known source, are untouched; a source that is not leftmost (a join's right side) does not trigger it. A user's real query on `pbip` with an unknown `ASEdog()` went from five errors to one.

Checked against real data, not only fakes: the 7 distinct queries in the user's run log that ran successfully, run against the cached schemas of the two clusters they ran on, got no diagnostics, and a deliberately wrong table on each cluster got `KS204`, so the analysis was active (probe in the session scratchpad, not kept). Remaining risk: names the service knows that the library (Microsoft.Azure.Kusto.Language 12.4.0) does not, or a function defined in a database the query does not name; the option above is the escape. Not built: diagnostics from an offline schema file, a severity setting, and quick fixes.

## Entity groups and macro-expand

`macro-expand EntityGroup as X (…)` runs a subquery over the entities of an entity group. The analysis library binds it completely (`X.Table`, the columns after it, completion of both) but only when the group is a symbol of the database. The server loaded tables, external tables, materialized views and functions only, so the name of a stored group, and every name under `X`, came back `KS142` and completion offered nothing (found by the user; reproduced with a probe against the library, which reported nothing wrong once an `EntityGroupSymbol` was added to the database).

`SchemaManager.LoadDatabaseAsync` now asks `.show databases entities` for `EntityGroup` rows too (documented to be one of the entity types, and readable with the permission to read the schema) and builds `EntityGroupSymbol(name, definition, doc)` from each, with the definition from the row's `Content`. Not verified: what `Content` holds for such a row, since the documentation says only "entity content, if applicable" and no cluster with a stored group was at hand. A group with no content is therefore read with `.show entity_groups` (`Name`, and `Entities`, an array of strings such as `cluster('c1').database('d1')`; documented as Database Admin only). A refusal is logged and the group is kept without entities; the library does not hold an empty or unreadable definition against a query (probed: no errors, nothing completed), so the load of the database does not fail. The library reads the definition bare, in brackets, after `entity_group`, or as a JSON array of strings, so the server does no parsing of its own (a normaliser written first was removed after a probe showed the library already handles the array).

The entities of a group are other clusters and databases. `GetClusterReferences` and `GetDatabaseReferences` follow a bound group into its definition, so `LoadReferencedSchema` loads them and `SchemaIsLoaded` waits for them, like a `cluster(...)` in the query. A group is only known when its own database has arrived, and `LoadReferencedSchema` ran only when a file was opened or edited, so `RepublishDiagnosticsAsync` (run on every `SchemaManager.Changed`) calls it too; without that the other clusters were asked for at the next keystroke. A group written in the query (`macro-expand entity_group [...] as X`, or `let G = entity_group [...]`) is covered by the same references.

`SchemaCache.FormatVersion` went from 1 to 2: a schema cached before groups were loaded would otherwise be used for as long as it stays fresh (an hour), and look as though the fix had not worked. The first start after the change fetches every schema once.

Tests: `EntityGroupTest` (server, 7): group names, tables and columns completed; a name under a group checked without a keystroke (the cluster is delayed so that the group arrives after the file is open; the test fails without the `LoadReferencedSchema` call); the `.show entity_groups` fallback and its refusal; the four ways a definition may be written, including a list of two databases; groups written in the query; and cached groups used without the cluster. Not built: the number of groups in the refresh message (`Refreshed the schema of …: 2 tables, 1 function.`), and anything for `macro-expand` beyond what the library gives (hover and signature help on a group are the library's).

## Refreshing the schema

A `↻ Schema: <age>` lens (`CodeLenses.SchemaTitle`) follows the connection lens of each query that has a cluster and database. The age is when the schema in memory was fetched, from the cache file's `fetchedAt` when it came from the cache; `loading…`, `refreshing…` and `not loaded` are the other states (`SchemaManager.StatusOf`, kept per `host/database`, with a `Changed` event that makes the server send `workspace/codeLens/refresh`; not before the client's `initialized`). Its command is `kusto.refreshSchema [cluster, database]`, not a Zed action: Zed already sends any lens command that is not `zed.dispatchAction` to the server as `workspace/executeCommand` (as for `kusto.connection`), so this needed no change in the fork. The server answers at once, fetches in the background (`SchemaManager.RefreshAsync`: the database list and the database, ignoring the cache's age, keeping the old schema on failure) and reports with `window/showMessage` (type 3 with the counts, or type 1 with the reason), which Zed shows as a notification.

## Query parameters

Design from the VS Code fork (`docs/FORK_DESIGN.md` there): a query declares `declare query_parameters(raid:string)`, the values come from the active profile of `.kusto/parameters.yaml` or an adjacent `<name>.parameters.yaml`, and go to Kusto as native parameters (`properties.Parameters` of the v2 request, strings parsed by the service by declared type; proved against the help cluster by the ignored live test `passes_values_for_declared_query_parameters`), never pasted into the text.

- `crates/kusto_client/src/parameters.rs`: `ParameterProfiles::parse` (serde_yaml_ng; an active name that is not a profile is no active profile), `with_active_profile` (edits only the `active:` line), `template`, `sidecar_path`, `declared_parameters` (a scanner that skips comments and quoted text), `parameters_for_query` (only declared names the profile has). `QueryRequest.parameters` adds `properties.Parameters` to the body when not empty.
- `crates/kusto_results_ui/src/query_parameters.rs`: `ParameterFiles::of_editor` (sidecar, and the worktree's `.kusto/parameters.yaml`), `load` (sidecar if it exists, else the project's; a file that cannot be read fails the run instead of running without values), the Picker (profiles, `No active profile`, `Edit profiles…`; writes the file with `write_active_profile`), and the open actions. The run path calls `load` in the run's task.
- Server (`QueryParameters.cs`, YamlDotNet 16.3.0): reads the same files, finds the declared names and whether each has a default, and `CodeLenses.For` adds `Params: <profile>` (`none`, `(no value for …)`, `cannot read <file>`) that dispatches `kusto::SelectParameterProfile`. It watches the files of open documents (not creating `.kusto`) and refreshes the lenses when one changes; workspace folders come from `initialize`. The declared names are tested against one shared file, `fork-docs/samples/query-parameters.json`, in both languages. Not shared: file parsing, which is tested in each language on its own.
- **"Make Active" lens in the profiles files (built):** `extension.toml` lists `YAML` in `[language_servers.kusto-lsp] languages` (`YAML = "yaml"` in `language_ids`). Zed registers an extension's server per language name and YAML's default `language_servers` is `["..."]` (every registered server), so no settings change is needed (read from `extension_lsp_adapter.rs` and `default.json`; confirmed working in a real window by the user, after **Rebuild** of the dev extension, which a changed `extension.toml` needs: a restart alone leaves Zed's `extensions/index.json` with the old manifest). Every YAML file therefore reaches the server, which ignores all of them except `.kusto/parameters.yaml` and `*.parameters.yaml` (`QueryParameters.IsYaml`, `IsProfilesFile`): those are kept in `profilesFiles` (never in `documents`, so they get no query completion, hover or diagnostics), and `CodeLenses.ForProfilesFile` gives `✓ Active` (`kusto.noop`) or `Make Active` (`zed.dispatchAction` with `kusto::MakeParameterProfileActive { name }`) on the line of each key under `profiles:` (`QueryParameters.ProfileKeys`, from YamlDotNet's marks), from the text of the editor. `query_parameters.rs` handles the action: it takes the active editor's buffer (a lens click focuses the editor), checks the file name, computes the new text with `with_active_profile` and applies only the differing part (`minimal_edit`) to the buffer, then saves it. Downside: opening any YAML file starts the .NET server. The other option, a separate "Kusto Parameters" language with its own YAML grammar, was not taken.
- **Values in the file (built, asked for by the user):** `// :setParam("name", "value")`, `// :clearParam("name")` and `// :clearParams()` use the directive line that sets the cluster and database, with the same rules (below the line until changed, the space after the slashes optional, a directive in a query's block reaches that query). The grammar was widened from one string argument to a list of them, shared by both implementations: a known name with the wrong number of arguments, a name that is not a parameter name, or an unquoted value is not a directive and gets the existing `directive` warning. Arguments have no escapes (a value with one kind of quote uses the other), because the directive is typed by hand and a Windows path should not need doubled backslashes. State is now `DirectiveState { connection, parameters }` (`state_up_to`, `state_for_selection`; `ResolvedQuery.parameters`) in Rust and `DirectiveState`/`StateBefore` in `ConnectionDirectives.cs`. Precedence is file, then the active profile, then the declaration's default; only declared names are used, as for profiles (`parameters_for_query` takes the file's map). Because the file's values join the profile's in `QueryRequest.parameters`, they reach the service as native parameters, the run log, the history Rerun, the `parameters` and the stored `Query` of the result (`let raid = 'abc-123';`) and the Copy lens with no further change. The lens title is `Params: <profile> + file: <names>`, `Params: file: <names>` or the old forms (`QueryParameters.Describe` takes the file's values, `CodeLenses.For` the resolved state per query). Completion offers all five directives, with a stop in each argument. Tests: `parameter-directives.json` (14 cases) checked by `directives::tests::the_shared_parameter_cases_resolve_as_expected` and `ParameterLensTest.test_the_shared_directive_cases_give_the_parameters_the_editor_computes`, `parameters::tests::a_value_the_file_gives_comes_before_the_profiles_and_needs_no_profile`, seven run tests in `run_query::tests` (sent instead of the profile's, no profile needed, cleared goes back to the profile, undeclared not sent, a selection, the copy and the stored query), and in the server the completion, the warnings and five lens tests. Both shared tests were checked to fail with `clearParams` made a no-op. Not built: values with escapes, bare numbers and booleans (`setParam("count", 5)` is a warning; write `"5"`), a directive that gives a value to a name the query does not declare (it is ignored, like a profile's), and showing a value's origin on a copy.
- **Completion of `declare` and of parameter names (built, asked for by the user):** probed first: the library offers no `declare` among the statement starters (`let`, `set`, `print`, … are `QueryPrefix` items; `declare` is only offered after `declare `, as `pattern` and `query_parameters`) and inside `declare query_parameters(` offers only `:` and `[`. `Program.Complete` adds a `declare` keyword item with `let`'s sort text whenever the library offers `let` (its way of saying a statement can start), and `CompleteParameterName` answers instead of the library where `QueryParameters.NameAt` finds a name being written: it blanks comments and string contents (keeping positions), tracks the parentheses of each `declare query_parameters(` up to the cursor, and accepts the cursor when the text since the last top-level comma is only a partial identifier (so after a colon, in a default value or after the closing parenthesis it says no). A text scan rather than the syntax tree, because the code being completed is incomplete and the parser's recovery is not something to depend on. The names come from `QueryParameters.Known`: the `// :setParam` names above the query, the active profile's, then every other profile's, sorted in that order, minus the names the declaration already has (computed without the part being typed). Only the name is inserted. Tests: `LanguageServerTest` (two: `declare` where a statement starts and not inside a query) and five in `ParameterLensTest`. Checked to fail with the exclusion of declared names removed and with `declare` not offered. Not built: guessing the type from a profile value, and offering names while a profiles file cannot be read.
- Not built: the status-bar picker (Zed has no equivalent surface for a lens-less file), importing profiles from the clipboard, completion of parameter names in the YAML, and schema-aware checking of a value against its declared type.

## Functions in the file

Asked for by the user after the parameter directives: functions, and then values, defined in the query file and added to the queries that use them. Explored first (probes against `Microsoft.Azure.Kusto.Language` 12.4.0, in [`kusto-inline-functions-design.md`](kusto-inline-functions-design.md)), then built as proposed; the user chose the marker `// :functions`, adding only the functions a query uses (with those they use), and showing the added `let`s in Copy and the stored query.

- **Syntax and scope.** A block with the line `// :functions` is not a query (`query_text.rs` `blocks`, `QueryBlocks.Find`), and its `let name = …;` statements are definitions (first only functions, `let name = (parameters) { body };`; the user then asked for scalars, and every `let` counts, whether it is a function, a scalar or a table). They apply to every query below the block like the parameter directives do (`DirectiveState.functions`, `StateBefore`): a later definition of the same name replaces it where it was, so a function defined after it that uses it keeps coming after it, and `// :clearFunction("name")` and `// :clearFunctions()` take them away. The two implementations agree through `fork-docs/samples/function-definitions.json` (15 cases). The Rust side reads statements with a scanner (`functions.rs`: strings, `//` comments and brackets decide where a statement ends; a definition is `let name =`; a last statement without its `;` gets one), the server with the library's parser (`InlineFunctions.Read`, every top-level `LetStatement`; a `FunctionDeclaration` counts only when its body starts with `{`, because `let f = (x:long);` parses as a function with no body, which is a mistake the block's own diagnostics report and which the two sides do not agree on). Not shared: the statement text itself, which only the editor needs.
- **Running and copying (editor, no server needed).** `functions_used_by` (which covers values too) takes the words of the query outside comments and strings, adds the functions with those names and, transitively, the ones their texts use, in definition order, and leaves out a name the query defines with `let` itself (the library reports `KS201` for a repeated `let`, and a `let` shadows a database function without error, both probed). A word that is also a column adds an unused `let`; the library checks the body of an unused `let` (`KS142`), which is why only the used ones are added. `with_functions` puts them after the leading `declare`/`set` statements (a body that uses a declared parameter binds only after the `declare`, probed: `KS142` otherwise), or before the first line of code when there are none, below leading comments, and never makes a blank line, which would split the stored query into two. `QueryRequest.functions` holds the statements and `text_to_send()` the text the service gets; `query` stays as written, which the run log, the history, the lens key and `cancel_newest` use. The copy and the stored query add the functions first, then ask the server to qualify that text (so tables in function bodies are qualified), then turn `declare` into `let` statements (`portable_query`), which gives the order parameters, then functions, then the query. The run log records `functions` in the three records, `HistoryEntry` and `RerunQuery` carry them, so a history Rerun sends the same text; Rerun in a result tab needs none, because its stored query already has them.
- **Editing (server).** The definitions in scope become `FunctionSymbol(name, parameters, body)` members of the database the query runs on (`InlineFunctions.Apply`: `WithDatabase(database.AddMembers(…))`, which also works before any schema has loaded because `DatabaseSymbol.Unknown` is open), through `Program.GlobalsOf`, used by completion, hover, signature help, colours (`SemanticTokens.Build` now takes the state) and diagnostics. This needs no offset arithmetic, which a prepended `let` would (five places add `block.Start`), and the qualifying command is not affected because the editor sends it the text with the `let`s. A functions block is analysed as code (`DiagnosticsOf` accepts `IsFunctions`, `LoadReferencedSchema` too, so a `cluster('x').database('y')` in a body loads), because a mistake in a symbol's body is reported only at the call (`KS108`) and a syntax error in it not at all. Parsing is cached by block text (64 entries).
- **Values (the scalars the user asked for next).** Probed first: a `FunctionSymbol(name, "()", "{ expression }")` is used by its bare name (`Events | where Value > threshold`), is typed as the expression is (`long`, `timespan`, `dynamic`, a table), a type error against it is caught, a column of the same name wins, and hover says `(function) threshold(): long`. The library also accepts `threshold()`, which the service rejects for a `let`, so the server does two things: completion offers a value without parentheses (the library offers `threshold()` as a snippet; `Complete` keeps the label and the text bare when the name is a value of the file), and `InlineFunctions.CallsOfValues` reports a call written with parentheses as an error with the code `inline-value` (only where the symbol is the file's own, so a `let` of the same name in the query is left alone; it analyses the query for this even before a schema has loaded). Colours are the function colour, since the symbol is one. The editor needed only to stop asking for a function shape.
- **Completion of the directives:** `functions`, `clearFunction("…")` and `clearFunctions()` after `// :`; the marker and the clearing directives with a bad argument get the existing directive warning.
- **Tests.** `functions::tests` (13), `query_text::tests::a_block_of_function_definitions_is_not_a_query`, `directives::tests` (the shared cases and two for the cursor and the selection), `run_log` and `history` (functions kept and surviving the records that follow the start), and seven in `run_query::tests` (sent with the query and logged as written; none added when unused; after the `declare`; copy order with a parameter; the stored query; a rerun sends the same text; a value, with the function that uses it, in a run and a copy). Server: the shared cases through colours (`SemanticTokensTest`, which counts a call as a function only when the symbol is known; queries that define the name themselves are skipped, since a local `let` is coloured too), and in `DirectiveTest` the block not being a query, a syntax error reported in a definition, hover and completion below the block only, a cleared function, the directive warnings, and four for values (typed, completed bare, the call form reported, a `let` of the query's own); in `SchemaDiagnosticsTest` an undefined or a cleared function is reported as an unknown name and a defined one is not. Checked to fail with `clearFunctions` doing nothing, with a functions block counted as a query, with a rerun that forgets the functions, with the functions put before the `declare`, and with values not read, completed as calls, or not reported when called.
- **Not built:** a lens or hover that says which block a definition came from, a value coloured as a variable, ignoring a name after a dot when deciding what a query uses (a column or property with a value's name costs an unused `let`), checking that a definition used in a query exists before the run (the service says), and following an `external` reference inside a body for the schema check of the query that calls it.

## Code lenses (RUN-9, first slice)

Per-query lenses above each blank-line-separated query, from the language server, on two lines. The first line is what to do: `▶ Run`, `<spinner> Running… <elapsed>` with `Cancel` (the server re-sends the lenses four times a second while any run is going, because a lens is plain text from the server; if Zed's lens blocks flicker at that rate, drop the spinner and refresh once a second), `Results (<rows>)` (straight after Run or Cancel), for a query that declares parameters `Params: <profile>`, and `Last run: <time>, took <duration>` (the rows stay here only when the run left no result file for Results to show) or `Last run failed: <message>`. The second line is `Copy`, where it runs (the connection), `↻ Schema: <age>` (click to refresh) and `Copy CID`. In a profiles file, `Make Active`. Enable with the Zed setting `"code_lens": "on"`.

- **Second line** (tried at the user's request, not yet looked at in a real window): the first line was one block, so a long connection lens could push `Results` out of reach, which is why Results was moved next to Run. The server marks a lens for a line below with `data: {"zedLine": 1}` (`CodeLenses.For`), and the editor (`display_line_of`) groups the lenses of a row by `(row, line)` and gives each group its own one-line block above the row, with the line as its block priority so that the blocks stay in order whichever is inserted first. A lens with no such data is on the first line, so another server's lenses look as before. Tests: `test_code_lens_server_can_ask_for_a_second_line`, and `test_the_last_run_is_on_the_first_line_and_where_the_query_runs_on_the_second` in the server tests. Not settled: whether Params, Schema and Copy CID belong on the line they are on (Last run was first on the second line, and the user moved it to the first).

- **Copy lens** (`kusto::CopyQuery`, `copy_query` in `run_query.rs`; asked for by the user, not yet looked at in a real window): copies the query at the cursor so that it means the same wherever it is pasted, and the same text is the `Query` of the `.ktt` file. The user's two options were a comment with the cluster, or qualifying the names; qualifying needs the schema, which only the language server has (`Kusto.Language` binds names), and the editor reaches it over the connection Zed already has: `workspace/executeCommand` with `kusto.qualifyQuery` `{ text, cluster, database }` answers `{ text, complete }` (`PortableQuery.cs`, `Program.QualifyQuery`), sent from `qualify_query.rs` with `LanguageServer::request` to any running server named `kusto-lsp` of the project (so reruns and threads use it too), with a five second limit. A name is qualified when its symbol is a member of the query's own database and it is not after a dot (`PathExpression.Selector`), so `let` variables, columns, already qualified names and what a database-returning function selects are left alone (`Home().StormEvents` gives `cluster(..).database(..).Home().StormEvents`). The server starts loading the schema of a database it is asked about and does not have, for the next copy; this one is `complete: false`. Without an answer the editor puts the two connection directives above the query. Parameters need no server: `kusto_client::portable_query` replaces each `declare query_parameters(...)` with `let` statements (`with_parameter_values`) from the values the run would use, else the declared defaults, as literals of the declared type (a value that is not written like its type goes through `tolong("…")` and the like), and leaves a parameter with no value, or of a table type, declared. A control command is left as it is. The lens is the first of the second line (`CodeLenses.cs`), and `QueryThread` answers the action for a thread's editor like `RunQuery`. A run starts the qualification beside the query and waits for it only after the answer arrives (`save_run`), so a slow server never delays a run. Tests: `portable_query::tests` (15), `PortableQueryTest` (server, 9), and in `run_query::tests` the copy of a query with and without a server (a fake `kusto-lsp` in the project answers the command), the profile's values, the stored query, and `copying_from_a_thread_copies_the_query_of_that_thread`. Consequences: the history list and the run log still hold the query as written, so the lens, the list and Rerun in the history are unchanged; Rerun in a result tab repeats the text the file keeps, which is not the text the lens matches, so that rerun's last run shows on no lens, and it sends only the parameters its text still declares (`ParameterSource::Values` is filtered by `declared_parameters`, because the file's values outlive the declaration); a file name made from the stored query leaves the `cluster(..).database(..).` prefix out (`history::without_qualification`). Not built: colours on the clipboard (Zed's clipboard has plain text only, CPY-11), qualifying the names in a query for the `Query` of a run when the server is not running (it gets the directives instead), and a setting to turn the qualification off.
- **Fork change** (`crates/editor/src/code_lens.rs`): a lens command `zed.dispatchAction` (`DISPATCH_ACTION_COMMAND`) is handled in the editor instead of being sent to the server. Its arguments are an action name and optional JSON data; the editor builds the action with `cx.build_action`, focuses itself and dispatches it. The click handler already puts the cursor on the lens first. Test: `test_code_lens_dispatches_a_named_action_instead_of_asking_the_server`. The only other change in Zed is the second line, below.
- **How the server learns about runs:** it does not talk to the editor. Each run appends `started`, then `finished` (rows, duration, saved file) or `failed` or `cancelled` to `<data dir>/kusto/history/runs.jsonl` (`kusto_client::RunRecord`, written by `log_run` in `run_query.rs`, trimmed to the last 400 records). The server (`RunLog.cs`) reads the tail of the file when asked for lenses, matches by the query text without comments and layout, and watches the file to send `workspace/codeLens/refresh`. The data directory reaches the server as `KUSTO_ZED_DATA_DIR`, which the extension derives from its working directory (`<data dir>/extensions/work/kusto`).
- **Actions** in `run_query.rs`: `kusto::CancelQuery` (cancels the newest running query at the cursor, else the newest run), `kusto::ShowResult { path }` (shows any saved result in the panel, or a tab), `kusto::CopyClientRequestId { id }`. Lenses that only show text name `kusto.noop`, which the server accepts, so that Zed makes them clickable.
- Not built: Select, Copy and Format lenses (RUN-9), a lens for a query the server cannot tell apart from another with the same text, and two Zed windows writing the log at the same moment can lose a record.

## Saving a query as a snippet

Asked for by the user: right-click a query and make it a snippet. `kusto::SaveQueryAsSnippet` (a command of the palette and an entry of the editor's context menu, **Save Query as Snippet**) takes the selection, or the query at the cursor as a run would (`query_text_at_cursor`), asks for a prefix in a small prompt (`query_snippet.rs`, shaped like `open_url_modal.rs`) and adds the snippet to `<config dir>/snippets/kusto.json`, which Zed's snippet provider already watches, so it completes without a restart.

- **Fork changes in Zed:** the action is declared in `zed_actions::kusto`, because the context menu in `crates/editor/src/mouse_context_menu.rs` has to name it and `editor` cannot depend on `kusto_results_ui`; the menu entry is shown when `window.is_action_available(&SaveQueryAsSnippet)`, the way Run to Cursor is. `kusto_results_ui` handles the action per editor with `register_action_renderer`, only while the editor shows a buffer whose language is `Kusto`, so the entry is in the menu of `.kql` files and in no other. Both edits are a few lines, to keep merges of upstream Zed easy.
- **What is saved:** the text as written, one line per `body` entry, with `$` and `\` escaped (`snippet::escape`; a test parses the escaped text back to itself). Nothing is qualified, no parameter is replaced and the functions a file defines are not added, so a query that calls one of them needs it where the snippet is inserted. The prefix is also the name (the key of the file's object).
- **Writing the file** (`snippet_provider::add_snippet`): the snippets file is commented JSON that people edit, so it is not parsed and written back. The new entry is placed after the last one with `end_of_entries`, a small scanner that skips strings and comments, because `settings_json::replace_value_in_json_text` puts a new key before the first one, which moves a comment from the snippet it describes to the new one (found while writing the tests). A comment on the line of the last snippet stays on that line, and a comma is added or not as the file needs. Formatting is `settings_json::to_pretty_json` with the file's own indentation (2 spaces when it has no snippet to take it from). A name the file has gives `AddedSnippet::NameTaken`, a file that is not a JSON object an error, and neither changes the file.
- **Tests:** `snippet::tests::test_escaped_text_parses_back_to_itself`; in `snippet_provider` the exact text for a file with comments, with a trailing comment, with only comments, with braces and quotes in strings and comments, and the cases above through a `FakeFs`; in `query_snippet::tests` the offer only for Kusto buffers, the cursor and the selection, `$` and `\`, an empty prefix, a name that is taken, and a file with no query. The prompt is exercised by calling its handler, because the workspace of the tests is not rendered inside a `MultiWorkspace` (see `run`).
- **Not built:** a lens (the lens lines are full), a description or tab stops chosen in the prompt (the **Open** button on the notice is for adding them), saving the file's `// :functions` along with the query, snippets for other languages, and replacing a snippet of the same name.

Decided with the user: the queries of a thread are a `.kql` file in the user data directory (a query worth keeping is moved into a project), and results always open as tabs whatever `kusto.results_location` says.

Run `cargo test -p kusto_results_ui -p agent_ui -p sidebar --lib`.

## Known issue: large results are very slow to download in a debug build

Judge speed in a release build (`cargo run --release -p zed`, or `--profile release-fast`). In a debug build (`cargo run -p zed`) a result of about 13 MB took 250 to 290 seconds to download; in a release build the same query matches VS Code (about 2 seconds).

What was measured (the `kusto:` lines in `~/Library/Logs/Zed/Zed.log`, which Zed writes there instead of the terminal when stdout is piped):

| Stage | Time |
| --- | --- |
| token audience, new token | 0.4 s, 0.7 s (once; later runs reuse both) |
| response headers | 0.09 s |
| reading the 13.4 MB body | 288.9 s |
| parse, serialise, save, open the tab | 0.1 s, 0.2 s, 3 ms, 0.24 s |

How it was narrowed down, with the ignored tests in `crates/kusto_client/tests/live.rs`:

- The same query through `ReqwestClient::new()` takes about 1.4 s, even in a debug build. Through `ReqwestClient::proxy_and_user_agent` (what `crates/zed/src/main.rs` builds for the app) it takes 250 to 283 s.
- The two clients differ in HTTP version: the plain clients negotiate HTTP/2, the app's negotiates HTTP/1.1 (`http_version_by_client_construction`). The app's client uses a preconfigured rustls config (`http_client_tls::tls_config`), which seems not to offer h2.
- A 1 MB result is fast with every client in debug and release, so the slowdown needs a large response, and a release build does not show it.
- Not the cause: gzip (runs before and after we asked for it were both slow), JSON parsing, saving, opening the file, the grid, the proxy (none is set) or the token. Compiling `hyper`, `hyper-util`, `httparse`, `rustls` and `bytes` with `opt-level = 3` in `[profile.dev.package]` did not help (about 248 s), so it is not just unoptimised HTTP code. That change was reverted.

Not found: why an HTTP/1.1 body read is slow only in a debug build. Ideas, cheapest first: log chunk sizes and the time between reads of the body in `KustoClient::send`; try `read_to_end` through a larger fixed buffer; build a client with h2 for Kusto only (a second `reqwest` client in `kusto_client`, leaving the shared Zed client alone); look at `ReqwestClient`'s `StreamReader` and `into_async_read` path for a debug-only cost. Do not change the shared client's TLS config without checking what else relies on it.

Reproduce:

```sh
KUSTO_TIMING_QUERY=<file> KUSTO_TIMING_CLUSTER=<url> KUSTO_TIMING_DATABASE=<db> KUSTO_TIMING_APP_CLIENT=1 \
  cargo test -p kusto_client --test live time_a_query_from_a_file -- --ignored --nocapture
cargo test -p kusto_client --release --test live http_version_by_client_construction -- --ignored --nocapture
```

Also found at the same time, and fixed: every run built a new client and so asked for the token audience and started `az` again. The client is now shared and caches both (a repeat run went from about 470 ms to about 60 ms), and it asks for gzip because Zed's reqwest has no decompression feature.

## Known gaps

- Large downloads are very slow in a debug build (see above); the cause is only partly understood.
- The settings reach the server through a file, not through the LSP: Zed writes the `kusto` cluster and database to `<data dir>/kusto/defaults.json` (`run_query.rs`, `share_defaults_with_language_server`) and the server follows it (`DefaultsFile.cs`), so a change applies without a restart and wins over `lsp.kusto-lsp.initialization_options`. Only the user-level `kusto` values are written, as for running.
- A cached schema is replaced on its own only when it is more than an hour old (option `schemaCacheMinutes`); the `↻ Schema` lens refreshes it now, but there is no palette command for it (a Zed action would have to send `workspace/executeCommand` to the server, which no code in kusto_results_ui does yet) and no way to refresh every database at once. The token audience is cached in memory (editor and server) but not on disk, which would save about 0.4 s on the first run after starting Zed.
- Diagnostics check names only against a loaded schema (see Schema-aware diagnostics); a file with only an offline `.kusto-schema.json` still gets syntax errors only. Signature help finds unqualified function names only, and a repeatable parameter such as `strcat`'s highlights the wrong argument.
- The Results panel is fixed to the bottom dock; there is no Query tab, no Save As and no history picker.
- Pruning protects only the results open in the workspace that ran the query; a result open in another Zed window can have its file deleted (it keeps showing from memory). Results older than the run log's 200 runs are on disk but not in the picker until pruned.
- Two Zed windows writing the run log at the same moment can lose a record.
- Shift+Enter in a `.kql` editor runs the query and no longer inserts a newline (the VS Code binding).
- Query threads are not finished: see the table in spec section 5.10.
